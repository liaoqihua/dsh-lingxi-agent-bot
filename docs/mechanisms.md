# 灵犀 · 模块抽象设计

> 这篇只讲**为什么长成这样**：每个模块负责什么、边界在哪、彼此靠什么契约协作、当初为什么这样取舍。
> 不逐个讲函数与字段、不抄默认数值——现状细节见 [communication-and-data-model.md](communication-and-data-model.md)，可调参数以设置页和 `config.json` 为准。
> 读者：要改这块代码的人，以及每次要决定「这个功能该加在哪一层」的人。

## 0. 定位与术语

灵犀做的事可以压成一句：**把 IM 上的聊天接成一台有理有据的 DSH 机器人**——机器人是唯一主体，聊天只是它跟人见面的场所。同一台机器人在私聊和群聊里是同一个人，但每个聊天各有自己的会话、上下文和开关。

本篇的用词固定如下，避免后文歧义：

| 词 | 指什么 |
| --- | --- |
| 机器人 | 一个独立个体：一条连接、一份人格、一份记忆、一份心情，用 `botId` 标识 |
| 聊天 | 用户可见的一处对话：某个机器人下的一个私聊或群聊 |
| 会话 | DSH 的执行单元，一个聊天绑定一个；属于宿主，不属于插件 |
| 注入 | 把状态投影成系统提示里的一块背景，不改会话内容 |

设计上反复要回答的三个问题：

| 问题 | 判断标准 |
| --- | --- |
| 这个状态归谁 | 由「谁能看到它」决定，而不是由「谁写它」决定 |
| 这个失败告诉谁 | 用户会不会误以为机器人正常陪伴？会 → 必须让人看见；不会 → 记日志 |
| 新能力加在哪 | 先归到模块地图里的某一层（接入 / 主体 / 适配 / 状态 / 表达 / 自主 / 装配 / 暴露），再决定要不要动会话桥 |

## 1. 三层归属与不变量

### 1.1 三层

| 层级 | 归属对象 | 放什么 | 生命周期 |
| --- | --- | --- | --- |
| 插件级 | 整个安装 | 灵犀自己的名字与兜底称呼、注入顺序、各模块的尺度参数、通道默认值、语音合成源、斗图开关 | 跟插件走，跨机器人共享 |
| 机器人级 | 一台机器人 | 凭据与连接、通道类型、群聊与访问名单、新会话默认装配、**对方称呼**、人格、记忆、心情、主动搭话的节奏与统计、语音节奏 | 跟机器人走，删除机器人时清掉 |
| 聊天级 | 一处对话 | 绑定的会话、回复目标、标题、主动搭话 / 主动语音的开关、时间线与计数 | 跟聊天走，删机器人时一并解除 |

**为什么这样切**：人格、记忆、心情描述的是「这个人」，不是「这段对话」。如果按聊天切，换一个聊天就变成另一个人——这恰恰是陪伴产品最不该出现的断片。反过来，「要不要在这儿开口」「能不能在这儿发语音」是社交分寸，必须按聊天分别决定，所以放在聊天级。

代价要明说：**群聊与私聊共享同一份记忆**。约束因此不放在状态层（不切割记忆），而放在表现层（群聊默认更克制：主动搭话、主动语音默认关）。哪天如果真需要「群聊里不提私聊的事」，那是一次状态模型改造，不该靠再加一个开关糊住。

### 1.2 不变量

这些是结构性约束，改动代码时应先确认它们还成立：

1. **主体唯一**：任何陪伴行为都能反查到 `botId`；查不到就拒绝，不做全局兜底。没有主体的状态是模糊问题，不是缺省值。
2. **绑定唯一**：一个聊天绑定一个会话，一个会话最多属于一个聊天。手动换绑与自动创建都必须满足，否则同时有两个聊天抢同一段上下文。
3. **状态不复制**：人格、记忆、心情只有一份，注入时按会话反查主体。会话里不缓存人格文本、不复制心情数值。
4. **配置单一来源**：新会话的装配只来自该机器人对应场景（私聊 / 群聊）的默认配置，没有第二处兜底。
5. **注入即投影**：装配时读状态、拼一块背景；失败返回空串，绝不阻塞对话。

## 2. 模块地图与依赖方向

| 层 | 模块 | 职责 | 明确不做 |
| --- | --- | --- | --- |
| 接入 | 通道（QQ / 微信 / 飞书） | 平台协议 ↔ 统一消息；连接状态；能力声明 | 不认识人格、记忆、心情；不决定谁能说话 |
| 接入 | 接入流程 | 授权状态机：授权完成前不产生主体 | 不写业务状态 |
| 主体 | 注册表 | 身份、凭据、新会话默认装配的声明 | 不持有活连接 |
| 主体 | 运行时 | 把声明变成连接：启停、重连、扫码、删除级联 | 不改写身份数据（除授权落库那一刻） |
| 适配 | 会话桥 | 聊天 ↔ 会话的绑定与双向管线、投递、排队 | 不拥有陪伴状态；不写平台协议细节 |
| 状态 | 人格 / 记忆 / 心情 | 机器人级状态的写入、衰减、召回与注入 | 不认识平台；不直接发消息 |
| 表达 | 斗图转换 / 语音合成 | 出站前的表现层转换与能力降级 | 不决定「什么时候该用」，那是提示词的事 |
| 自主 | 主动搭话 | 节奏、概率、目标选择、开口 | 不绕过聊天级授权 |
| 自主 | 定时激活 | 记录「提交时间 / 等待间隔 / 任务内容」，到点重新激活到原聊天 | 不排队、不猜目标聊天、不把激活当成对方的话 |
| 装配 | 提示词注册 / 注入健康 | 上下文块的顺序与韧性；注入被拿走时可见 | 不改宿主装配规则，只标记必需与对账 |
| 暴露 | 工具 / 设置接口 / 挂饰 | 同一状态的三个视图 | 不拥有状态，不做第二真相 |

依赖是一条直线，不回环：

```
设置页 / 工具 / 挂饰        人的面、模型的面、页面上的面
        ▼
陪伴状态（人格·记忆·心情）   自主行为（主动搭话·定时激活）
        ▼
     会话桥（聊天 ↔ 会话）
        ▼
     通道（QQ / 微信 / 飞书）  由机器人运行时按注册表的声明拉起
```

两条读法：

- 上层可以读下层，下层不反向调用上层。需要反查时由入口把查询函数传下去（例如「给我这个会话的机器人」），而不是让下层自己去找上层状态。
- 通道与状态层互不认识：一个管连接，一个管这个人是谁。删掉通道不会影响状态数据，删掉状态层只是让会话失去人格与记忆，连接照常。

## 3. 接入层：通道

**职责**：把平台的连接与事件翻译成插件内部的统一语言，再把统一出站载荷翻回平台消息。

抽象契约：

- **生命周期**：启动、停止、自愈重连。重连失败不外抛，收敛成连接状态里的失败原因。
- **入站**：平台事件 → 统一入站消息（谁、在哪儿、说了什么、图片、回复目标）。**幂等责任在通道**：平台给的去重凭据（消息 id、拉取游标）只有它知道，桥不该替它猜。
- **出站**：统一载荷（正文 + 图片）→ 平台消息。拆段是通道的事，因为平台限制是它最清楚。
- **能力**：语音、图片是可选能力。**用「有没有这个能力」表达差异，而不是到处判断通道类型**：上层据此决定要不要给模型提示（没有语音条就不注入语音规则）、要不要暴露入口（非 QQ 机器人没有「语音条」页）。
- **状态**：未配置 / 连接中 / 已连接 / 失败原因，供运行时与设置页读。

**边界**：

- **平台侧校验在通道**：secret 与签名回答「这条消息真的是平台发的吗」；群聊 @ 要求回答「这句话是不是对机器人说的」。两者都由通道静默处理。
- **业务授权不在通道**：访问名单、群聊开关、配置是否齐全，回答「这个人 / 这个群能不能跟机器人说话」。这类失败要让人知道（§11）。
- **凭据只属于机器人**：通道配置里的字段不构成「别的机器人可以借用的默认凭据」。同一台真实机器人被重复接入时，按稳定凭据去重——一个真实身份只该对应一个主体。

**接入流程是通道的伴生状态机**：授权完成之前，被接入的对象还不是主体（不落库）；一旦取消，就是终态，后续回调不能把它复活。这条约束的意义是：**主体一旦存在，就必须是可用的**，不留半接入的幽灵机器人。

## 4. 主体层：机器人与运行时

**注册表 = 声明**：身份是什么、连哪个通道、凭据、新会话默认怎么装配、哪些人 / 群能说话。它不持有活连接，所以机器人没启动时也能被随意读写。

**运行时 = 执行**：把声明变成一条真实连接，处理启停、重连、扫码、删除级联。

拆开的原因很实际：设置页要在「没连上」时也能改名、改默认配置、看状态；连接失败也不该让身份数据变得不可编辑。

**新会话默认装配是契约，不是策略**：

- 它是「新建会话长什么样」的声明，按私聊 / 群聊分段，是唯一来源，没有备用链。
- 它只作用于新建：已有会话用自己的目录、模型和权限，不该被「新会话默认」改动。
- 能省略的项留空表示「交给宿主默认」；目录与默认权限必须明确，因为它们决定 agent 在哪儿、能做什么——猜错比报错更糟。
- 默认权限走宿主的权限预设语义，而不是自己裸写权限字段。**不复制宿主语义**：宿主界面能解释这个会话，用户才理解得了它；自己拼一套组合，最终显示成「自定义」，等于把复杂度推给用户。

**删除语义**：断开连接、删除机器人状态目录、解除它的聊天绑定；**DSH 会话本身不删**——它属于宿主资产，用户可能还要在界面里继续用。

## 5. 会话桥

会话桥是唯一知道「聊天 ↔ 会话」对应关系的地方，也是唯一同时见得到通道与状态层的地方。它的存在让另外两层都不必知道对方。

### 5.1 身份与绑定

聊天标识 = 主体 + 通道 + 场景（私聊 / 群聊）+ 对方。同一对方在不同机器人下是两个聊天；同一机器人的私聊与群聊也是两个聊天。绑定只有一份记录，聊天记录是聊天状态的唯一真相源。

### 5.2 入站管线：顺序即设计

```
前置校验 → 登记聊天 → 确保会话 → 组装内容 → 投递
```

- **先校验后登记**：被拒绝的消息不该在聊天列表里留下痕迹。校验按「越便宜越早」排（主体存在 → 群开关 → 访问名单），拒绝的粒度也在这里统一（静默还是回话，见 §11）。
- **登记与投递分开**：收到消息就更新「最近有人说话」，即使这次会话拉不起来，主动搭话也知道对方刚来过。
- **组装内容**：**必带的时间块** + 可选的结构化上下文 + **必带的场景标记**（私聊 / 群聊 + 发言人）。时间和场景标记都不依赖「上下文增强」开关——一个是模型算时间的唯一依据，一个是社交前提，都不是可选装饰。引用消息也在这里并入。
- **时间只写一份**：`now`（日期 + 星期 + 时分秒 + 时区）与 `part_of_day` 由 `lib/time-context.js` 统一拼，入站与自主开口共用，两个入口的格式不会漂。
- **元数据不当对话**：来源块回灌历史或交给记忆/心情判断时，先过 `spokenTextOf()` 剥掉——不剥就会把自己写的背景当成「对方说的话」。
- **投递**：会话忙时按聊天排队，空闲时直接进入下一轮。取向是「不丢消息、按会话串行」，而不是「立刻回应」。不排队的选择等于把「打断当前回合」交给宿主，当前只作为语义保留。

### 5.3 确保会话：三段式

```
活着的实例 → 恢复已有会话 → 新建
```

- **门槛只压在「新建」这一段**：新会话默认配置缺失，只影响还没建过会话的聊天；已经绑好的聊天照常恢复、照常回话。把校验提前，会让「改了新会话默认」误伤老聊天。
- **新建后立刻挂工作区，挂接失败即整体失败**：回滚刚建的实例，不回落其他目录、不发首轮消息。理由很直白：错的目录会让 agent 在别人的项目里改文件，比这一轮不回更糟。
- **新会话要尽量和宿主自己建出来的一样**：用宿主登记的默认预设、宿主的权限预设、宿主的命名能力。差异越大，越难解释「为什么这个会话在界面上怪怪的」。
- 同一会话并发只创建一次；重复调用拿到同一个结果。

### 5.4 出站

```
攒正文（一个回合内多条助手消息）→ 回合边界 → 表达层 → 通道
```

- 以回合为单位发送：工具调用中间也可能有助手消息，逐条发会把一句话拆成几段。
- 回合失败且没有正文：给一句固定的安慰提示；用户自己取消的，不说话。
- 兜底：万一回合边界丢了，也有超时把已攒的正文送出去——**宁可晚一点，也不要吞掉回复**。
- 出站只走这条聊天所属机器人的连接；没有连接就不发，不借用别的机器人。

### 5.5 投递语义

- `followup` 是唯一入口，真人消息和主动搭话共用它。所以「主动开口」的回复自然回到原聊天，不需要第二条回执通道。
- 这也意味着：机器人主动说的话，和真人说的话一样会被记忆与心情看到。这是设计上想要的——它自己说的话也是经历。

## 6. 陪伴状态：人格 / 记忆 / 心情

三者共享一套契约：

| 契约 | 含义 |
| --- | --- |
| 机器人级 | 一份状态，所有聊天共享；注入时按会话反查主体 |
| 自动写入在回合边界 | 记忆与心情只在「这一轮说完了」更新，不逐条消息抖动；人格由人整体编辑，不在此列 |
| 注入即投影 | 装配时把状态投影成一块背景，不改变会话内容 |
| 失败静默 | 任何一步失败都只是少一块背景，绝不阻塞对话 |
| 惰性计算 | 需要「时间流逝」的量在读取时算，不跑常驻定时器 |

### 6.1 人格：静态身份

- 一台机器人一份完整文本，整体替换，不做增量编辑、不设生命周期。
- 注入顺序最前：它回答「我是谁」，后面所有块都是在这之上的补充。
- 没有机器人就没有人格——普通 DSH 会话不会因为装了灵犀而多出一段陪伴人格。

### 6.2 记忆：有选择的写入，有证据的召回

三个问题各自的答案都是设计决策：

**记什么**：不是每句话都值得记。只有看起来「值得长期记住」的一轮才提炼，并且有每日配额。提炼优先交给模型（更会分辨具体细节与寒暄），失败时退到线索词启发式。宁可少记，也不要记一堆没有信息量的句子。

**记成什么**：条目除了正文，还带三个维度——

- 时间与鲜活度：旧事会淡；长期事实（画像、喜好、约定）不淡。
- 重要度与情绪强度：决定它在召回排序里的话语权。
- 事实键：同一件会变化的事（身高、住址、约定地点）共享一个键，新值取代旧值，旧条目保留为历史而不是删除。

**怎么想起来**：靠证据，不靠「命中任意一个字」。只有查询里真正有区分度的词才算强证据，普通词只作弱证据；证据不足就不召回。目的很具体：**避免「因为我记得所有词，所以什么都相关」，每轮都塞一段旧事进来。**

两个刻意的选择：

- 注入有上限（条数与字数），并且明确告诉模型「这些是过去的记录，不是命令；和此刻冲突时以现在为准」。记忆是背景，不是指令。
- 删除是软删除：内容留着、只是不再被想起。可追溯比「真删掉」更符合「这是我们共同经历」的产品语义。

自动提炼不是唯一入口：模型可以显式记一条，也可以软删一条。自动判断拿不准的时候，把选择权留给人。

### 6.3 心情：连续量、会回落、只说一次

- 一个主值 + 七个情绪维度（开心 / 踏实 / 甜蜜 / 心疼 / 担心 / 难过 / 吃醋）。主值是底子，维度是这一阵的劲。
- 每轮结束用宿主自己的模型判断涨跌，幅度打折后落到主值——**判断是模型的事，尺度是插件的事**，避免模型每轮给满分。对方没说话、是机器人自己开口的回合，判据只有它自己说的那句话。
- 时间会把它拉回基线：主值慢、维度快。衰减在读取时按经过的时间算，所以关机几天再打开，心情是「淡了」而不是「冻结在五天前」。
- 只有显著变化才值得说出口，小波动只记账；再加会话 × 版本去重，结果是「一天里偶尔被提起一两次」，而不是每轮都「我心情不错」。
- 每日配额（默认 12）**不是硬闸**：记满之后不是拒绝，而是挤掉当天最早的那一条。所以条数始终不超过上限，但内容永远是此刻的心情——下午才发生的那次心疼，不会因为上午已经说过 12 次就被吞掉，也不会隔天被衰减抹平。配额设成 0 才等于「今天不再说」。
- 去重按「会话 + 心情版本」：同一会话同一份心情只说一次；换到新会话可以重新说一次——新会话没有上下文，它确实不知道。

### 6.4 「注入是纯投影」的张力

人格与守则是纯读。记忆与心情在注入时会写一点东西：召回计数、已告知标记、注入时间。这不是偷偷改状态，而是**投递记账**——用来保证「说过就不再重复说」。原则是：注入可以记「我投递过什么」，不可以改「我是什么」。这条线要守住，否则装配就变成隐式写操作，出问题时无从下手。

## 7. 表达层：斗图与语音

这一层解决的不是「能不能」，而是「会不会」。模型有工具不等于会主动用：工具说明只回答「这个能力是什么」，不会让它在合适的时刻想起来。所以每种主动表达都是同一套四件套：

```
能力（通道支持） + 提示词引导（什么时机用） + 出站转换（变成原生消息） + 记账（节奏与统计）
```

少一件就退化：只有能力 → 模型不知道什么时候用；只有提示词 → 一调用就报错；没有出站转换 → 用户看到一行奇怪的标记；没有记账 → 每轮都来一次。

### 7.1 斗图：标记 → 原生图片

- 模型只写标记；Web 会话由前端按标记配图，IM 里标记只是一行方括号文字。所以**出站前**把它翻译成图库里的真实图片，交给通道按图片发。
- 图库是别人的：只读索引，不 import、不改文件、不强制依赖。没有图库就原样返回正文，插件不能因此崩掉。
- 配不上的描述：把标记丢掉（不让方括号漏进聊天），只留一条日志。**宁可少一张图，也不要让用户看到内部标记。**

### 7.2 语音：能力最窄，所以最克制

- 只有 QQ 官方 Bot 能把音频作为语音条发出。于是「能不能发语音」是通道能力问题，不是配置问题：非 QQ 机器人根本不该看到语音入口，也不该收到「去发语音」的提示。
- 语音规则是一块独立的提示词，不是工具说明。工具说明只回答「怎么调」，这段回答「什么时候该主动用」：缺了它，语音就退化成需要用户点名才发的能力；缺了工具说明，模型又调不对。
- 开关分两层：插件级（合成开关 + 主动提示总闸）与聊天级闸门（某个聊天要不要）。和主动搭话同构：关掉任何一层就不生效，群里默认关。
- 合成源可插拔：借宿主的朗读路由，或任意 OpenAI 兼容 TTS。默认策略是「能借就借，借不到且自己配了就用自己」，都不可用就明说原因，不静默失败。
- 语音条是额外的一条消息，文字照常发；正文只留一两个字的占位，避免「念一遍再打一遍」。
- 合成关掉时，注入不再说「主动发」，而是明确一句「别调」——比留一段沉默更能避免模型反复撞同一个错误。
- 节奏是提示，不是拦截：刚发过语音时，下一轮注入补一句「这轮先用文字」。不硬拦的理由是最终判断权应该在模型——它可能真的遇到了更该用声音的时刻。

### 7.3 失败与降级

| 情形 | 设计上的处理 | 为什么 |
| --- | --- | --- |
| 通道没有该能力（如非 QQ 语音） | 不提供入口、不注入提示 | 注入了只会换来报错 |
| 素材缺失（图库配不上描述） | 丢掉标记，保留正文 | 内部标记不该漏给用户 |
| 合成失败（语音） | 正文照发，工具返回服务端原因 | 文字是主通道，语音是附加 |
| 发送失败 | 正文已发，图 / 语音作为附加项单独失败 | 一条附加表达不该拖垮整轮 |

共同点：**附加表达失败，不能拖垮这一轮的正文。**

## 8. 自主行为：主动搭话

主动搭话回答两个不同的问题，分别放在两层：

- **这台机器人现在想不想说话**：机器人级。节奏、概率、安静时段、每日上限、冷却、触发文案、统计。
- **在哪一个聊天里说**：聊天级开关。新会话默认私聊开、群聊关。

两个都开着才可能被挑中。这样「要不要主动」和「在这个群合不合适」是两个独立判断，不会互相污染。

### 8.1 漏斗

自动尝试依次经过：机器人开关 → 当日上限 → 机器人冷却 → 目标选择（开着开关的聊天、按最近有人说话排序、剔除刚开口过的）→ 对方空闲够久 → 不在安静时段 → 会话能拉起来 → 会话空闲 → 掷骰子。

顺序是有意的：

- 便宜且确定的先判，需要 IO 的后判（拉会话最贵）。
- 「刚开口过的聊天先歇着」与「整台机器人的冷却」共用一个值：冷却表达的是「别烦人」，按聊天算和按机器人算会得出同一结论，两个值只会让语义打架。
- 掷骰子放最后：只有前面都通过、真的要打扰了，才赌这一次。

### 8.2 概率

固定「每 N 分钟说一句」像闹钟。所以用补偿机制：这次没中，下次更容易中；命中后清零。频率由参数控制，节奏由概率控制——不僵硬，也不失控。

### 8.3 手动触发

用户点「现在说一句」时越过节奏、上限、空闲、安静时段和骰子，但不越过授权：没指定聊天时仍只从开着开关的聊天里挑；显式指定时按用户意图直取。**人可以绕过礼貌，但不能绕过「这个聊天没允许」**——除非他自己点名。

### 8.4 开口

- 走会话桥的 `followup`，和真人消息同一条路，所以回复自然回到原聊天。
- **正文自带时钟**：这类消息由插件直接塞进会话，没有宿主准备的回合上下文，模型看不到「现在几点」。不补这一段，它就会自己推算——把早上说成半夜、把隔了三天说成「刚刚」。所以注入正文由 `lib/time-context.js` 拼成：`now`（日期 + 星期 + 时分秒 + 时区）、`part_of_day`、对方最后一条消息是多久前、我上次在这里主动开口是多久前，最后才是机器人配置的那句「由头」。
- **顺手说清语义**：正文里写明「这是我自己想开口的由头，不是对方刚发来的消息」。否则模型可能把它当成对方的新消息来回应。
- 成功后同时更新机器人级时间线与聊天的「上次开口时间」：前者算冷却与配额，后者给聊天页显示活跃度。
- 回合收尾只拿「由头」本身（`proactivePromptOf()` 切掉上下文块）：那段背景是我们自己写的，当成对方说的话去提炼只会得到自我回声。
- 每次尝试都返回结构化理由。自动 tick 里被门槛拒绝属于正常状态，默认保持安静（否则日志会被「还没到时候」刷满）；真正掷骰与开口的结果进尝试日志。可观测性的要求是「能解释为什么没开口」，不是「记录每一次没开口」。

### 8.5 定时激活：把「等一会儿」变成一条新消息

主动搭话是「现在想不想说话」，定时激活是「到某个时刻要处理一件事」。两者复用的东西只有一件：会话桥的 `followup`。其余全部独立——定时任务不掷骰子、不看安静时段、不受每日上限约束，因为它不是「想说话」，是「有事要做」。

- **记录即事实**：一条任务在提交那一刻就写进 `bots/<botId>/schedule.json`，三样东西固定下来：提交时间、等待间隔、任务内容。页面只投影这份记录，不做第二份状态。
- **激活 = 一条带来源标记的入站消息**：`source.kind = 'companion-schedule'`，正文里写明「何时提交、等了多久、**现在几点**、这是你自己定的任务」。这样模型能分清「对方刚说了话」和「我自己定的闹钟响了」。单独给「现在」是必要的：只有「提交时间 + 等了 N 分钟」时模型得自己做加法，而 tick 有 15 秒粒度、卡顿后补激活还会更晚，算出来的时刻和真实时间就对不上。
- **忙就不打扰**：目标会话正在跑别的回合时，这一条不排队、不计失败，等下一个 tick。定时任务晚几分钟没有代价，插入正在说的半句话里有代价。
- **重启不丢，但重启有顺序**：记录落盘，插件启动时立刻补一次 tick；可那一刻通道还没起来（`botManager.startAll()` 在 ticker 之后跑，QQ 还要建长连接）。所以激活前先看通道：没就绪就当「还没到时候」，不排队、不计失败，下个 tick 再看。否则会碰上最坏的一种失败——一轮跑完了，回复却没有通道可回。
- **失败要有终点**：连续 3 次拉不起会话（配置缺失、聊天被删）就自动停用并留下原因；到期后超过 24 小时都没能激活（进程一直没开、或机器人一直没连上）不再补。记录不删，页面上看得到「试过、没成、为什么」。
- **不参与记忆与心情**：激活的那一轮是自己定的任务，不是对方的表达。把它当成「对方说的话」去提炼记忆，只会得到自我回声。

## 9. 提示词装配与预设韧性

### 9.1 装配顺序

| 块 | 位置 | 回答的问题 |
| --- | --- | --- |
| 人格 | 最前 | 我是谁 |
| 记忆 | 中 | 我记得的事 |
| 心情 | 中后 | 我此刻的底子 |
| 行为守则 | 很靠后 | 怎么说话、怎么用记忆 |
| 能力清单 | 守则之后 | 我有哪些工具、什么时候用、这会儿哪些用不了 |
| 操作性规则（语音等） | 最后 | 这一轮具体该做什么 |

越靠后越像即时指令：背景设定在前，和「这一轮怎么做」有关的在后。顺序本身是接口，改动会改变模型行为，不该当成排版。

### 9.2 为什么全部必需

Agent Preset 是宿主的权威装配，它**可以合法地**拿走插件贡献的提示词。已知两条路径：抑制「可选」运行时上下文；以及「完整人设」把某个前缀恢复成唯一段落（会把 section 顶掉）。我们不接受的结果是：用户换一个预设，机器人就**无声地**失去人格、记忆或心情。

对策分两步：

1. 核心状态一律注册为必需的运行时上下文。抑制器动不了必需的块；section 会被完整人设顶掉，所以守则也从 section 改成了 context。
2. 接受剩余风险，并让它可见：每块的注入函数被求值就记一笔；一个回合结束一笔都没有，说明这一轮装配里根本没有我们的上下文——写诊断、在状态接口里报出来。

这是「不能静默降级」在装配层的体现：我们既不想绕过宿主的装配权，也不允许失败无声无息。

### 9.3 代价

- 必需的上下文在预设声明「不要可选运行时上下文」时依然注入，这是刻意的。
- 守则改成 context 后，它进入对话历史的是 user-role 快照，而不是系统提示词。这是为「不被顶掉」付的代价。
- 必需也不是绝对的：宿主可以卸掉整个插件，或用更底层的方式重写装配。我们能保证的是「如果被拿走了，会有人说出来」。

### 9.4 能力清单：工具表回答不了的那两个问题

工具注册进宿主后，模型本来就能看到全部工具（名字、说明、参数）——「知道有」这件事不需要注入。`companion:capabilities` 补的是另外两件：

- **什么时候用**：工具说明写的是「是什么、怎么调」；「该不该用、什么时候用」是行为判断，只有提示词能表达。斗图与语音当初要单独一段，就是同一个理由。
- **这会儿能不能用**：语音要看通道（只有 QQ 官方 Bot 有 `sendVoice`），还要看合成开关和这个聊天的主动语音开关。不写清楚，模型只会反复撞同一个错误，或者绕过用户关掉的开关。

所以清单只做索引（一组工具 + 一句时机），细节留在各自的模块：语音的分寸在 `voice-prompt.js`，记忆/心情/人格的形态在各自的状态注入里。两条护栏：

- 清单是 `required` 上下文，和人格/记忆/心情同命运，不会被预设静默拿掉。
- 清单里的工具名必须和真正注册的工具**完全一致**（`tests/capabilities.test.mjs` 会核对两边）。加了工具却忘了写进清单，模型就等于拿不到这个能力；删了工具却留着清单，模型会去调一个不存在的东西。

普通 DSH 会话也会看到这些工具（注册是全局的），所以清单在那种会话里只给一行「这些能力只在机器人聊天里可用，不要调用」——比让它试一次再报错便宜。

## 10. 回合生命周期

```
IM 消息 / 主动触发 / 定时激活
  → 通道 / 定时器 → 会话桥 → followup → DSH 跑一轮
  → 回合边界（成功或失败）
       ├─ 出站：把正文送到原聊天
       ├─ 记忆：判断这一轮值不值得记（定时激活的回合跳过）
       └─ 心情：判断这一轮的情绪涨跌（定时激活的回合跳过）
  → 排队消息放行一条
```

- 收尾是**扇出**：三个消费者彼此独立、各自兜错。出站失败不该影响记忆，记忆失败不该影响回话。
- 顺序上出站优先：用户感知最重要，另外两个是内部记账。
- 只认回合边界，不认单条消息：一轮里可能说了好几段、调了好几次工具，只有边界能说明「说完了」。
- 注入类消息（宿主自己加的运行时上下文、时间提示等）不参与记忆与心情判断，否则会把自己生成的背景当成「对方说的话」。
- 子代理会话、非机器人会话直接跳过收尾——它们没有主体，也就没有「这个人的经历」。

## 11. 失败与降级

先把失败分档，再决定行为：

| 档 | 判据 | 处理 | 例子 |
| --- | --- | --- | --- |
| 伴生失败 | 用户不会察觉少了什么，或少了也不影响这轮对话 | 记日志，继续 | 注入失败、记忆提炼失败、心情判断失败、统计写失败 |
| 需要告知 | 用户以为在正常陪伴，但这次没做到 | 回一句带原因的话到原聊天 | 会话拉不起来（缺工作区等配置） |
| 整体拒绝 | 这条消息本就不该进入陪伴流程 | 静默或回一句提示，不投递 | 没有主体、访问名单、群聊未开、平台侧校验不通过 |

判断「静默还是回话」的标准不是错误大小，而是**会不会让用户误判机器人的状态**。访问名单拒绝保持静默：机器人替用户广播「你被拒绝了」既没礼貌也没意义；配置缺失必须回话，否则用户只会觉得「它不理我」。

其他几条立场：

- **幂等优先**：平台消息去重（凭据在通道）、排队有上限、注入有去重、冷却只有一个来源。重复比遗漏更难查。
- **出站不自动重试**：重复发一条完整回复，比漏一条更打扰；失败只记日志。
- **失败面要小**：一张图发不出去不影响正文，一段记忆没提炼出来不影响这轮回复，一台机器人出错不影响其它机器人。
- **不做兜底的地方**（都是刻意的）：没有主体不回落全局状态；工作区挂接失败不回落 `process.cwd()`；通道凭据不跨机器人借用；图库找不到不改写正文；语音不可用不偷偷改成发文字（那只是另一种打扰）。

## 12. 暴露面：设置页、工具、挂饰

三个面，同一份状态。

- **设置页**（人的面）：读写机器人、聊天、状态。写操作落在各自的数据所有者上：身份与默认装配在注册表，绑定与开关在会话桥，人格 / 记忆 / 心情在机器人状态目录。
- **工具**（模型的面）：记忆、心情、人格、发消息、发语音、定时任务。工具是插件内部能力，不是通用命令面板：每个工具都尽量绑定到明确的主体与聊天，反查不到时要么报错、要么返回空结果，不猜「最近的一台机器人」。注册本身就让模型看到了这些工具；「什么时候用、这会儿哪些用不了」由 `companion:capabilities` 一段注入说清楚（见 9.4）。
- **挂饰**（页面上的面）：右下角的心情挂饰。

共同契约：

- 只投影，不拥有状态；页面可以有短缓存，但不能变成第二真相。
- 写操作必须有明确归属（哪个机器人、哪个聊天）。唯一例外是「当前会话绑定的聊天」——那是有明确上下文的默认值，不是猜。
- 失败要可见：状态接口里带注入健康、连接状态与最近错误。设置页上的红字是产品的一部分，不是调试残留。

挂饰的特殊设计：**显隐由会话决定，不由开关决定**。页面广播「当前被主视图保留的会话」，挂饰拿它反查这个会话是不是某台机器人的聊天，是才挂上去。所以不需要「选择机器人」这种和对话无关的操作——挂饰显示的就是你正在看的那段对话所属的那台机器人。宿主答不上来时短暂重试，之后等下一次会话变化，而不是长期占位。

## 13. 扩展点与设计边界

### 13.1 往哪加

| 要加的东西 | 落点 | 要动的地方 |
| --- | --- | --- |
| 新通道 | 接入层 | 实现通道契约与能力声明 + 接入状态机；会话桥与状态层不用改 |
| 新陪伴维度（比如「关系阶段」） | 状态层 | 机器人级状态 + 一块必需注入 + 回合收尾的写入者；注入只做投影 |
| 新表达方式（比如卡片） | 表达层 | 能力 + 提示词引导 + 出站转换 + 节奏记账，四件套齐了再上 |
| 新的自主行为 | 自主层 | 独立漏斗 + 复用 followup；不要复制一条新的出站路径 |
| 新开关 | 先问归属 | 影响所有人 → 插件级；只影响一台机器人 → 机器人级；只在某处生效 → 聊天级。同一语义不要两层都放 |

两条给未来的提醒：

- **不要为了省一次查询，把状态复制进会话。** 一旦复制，就要处理同步、旧数据、删除；现在的「读时反查」是刻意选的简单。
- **不要用开关掩盖状态层的问题。** 群聊与私聊共享记忆是设计，不是缺陷；如果哪天它真的变成缺陷，应该改状态模型，而不是加第十个开关。

### 13.2 非目标

- 不做按聊天的人格 / 记忆 / 心情隔离（当前判断：人是同一个人）。
- 不做跨平台身份统一：同一个真人在 QQ 和微信是两个聊天，不合并。
- 不做多机器人共享状态：每台机器人是完全独立的个体。
- 不接管宿主的权限、工作区、会话标题语义：只按宿主的接口装配，不另造一套。
- 不做历史数据迁移：插件尚未发布，旧字段加载时直接忽略，按新模型解释。
- 不替用户决定「要不要这个能力」：所有主动能力都有开关，默认值按「更不打扰」选。
